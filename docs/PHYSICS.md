# Physics Notes

The first playable slice uses SMW-style 60 Hz fixed-step integer movement. The target for the finished port is a 100% physics match, so every approximation in this file is temporary until it is replaced by a reference-backed port and test.

Current implementation details:

- Position is stored in sixteenth-pixel units.
- Horizontal and vertical speeds use the same practical scale as SMW player speeds: one speed unit is `1/16 px/frame`.
- The full native horizontal max-speed, acceleration, friction/deceleration, and target sub-speed tables are exposed as `SmwPhysics.HorizontalMaxSpeedTable`, `HorizontalAccelerationTable`, `HorizontalGroundFrictionTable`, `HorizontalDecelerationTable`, and `HorizontalTargetSubSpeedTable`.
- Normal flat-ground horizontal caps now read the corresponding `kHandlePlayerPhysics_DATA_00D535` direction/P-meter entries directly: walking `0x14`, running `0x24`, and full P-meter sprinting `0x30`.
- P-meter updates use the native `kHandlePlayerPhysics_DATA_00D5EB` mode deltas `[-1, -1, +2]`; mode `2` returns mode `3` when it reaches `0x70`, which selects the sprint cap. The current C# bridge tracks full-P-meter running jumps as `RunningTakeoff` until landing so the airborne sprint mode is only carried from a native-style takeoff, not from every airborne full-meter state.
- Flat-ground acceleration now reads `kHandlePlayerPhysics_MarioAccel` for grounded left/right and run/walk movement. Turn-around acceleration uses the native walk/run entries `0x0280` and `0x0500` instead of the earlier temporary `0x0600` shortcut.
- Held horizontal movement now follows the native `HandlePlayerPhysics_00D742()` branch: reaching or overshooting a cap applies table drag back toward the target sub-speed instead of hard-clamping `XSpeed` and clearing subspeed. Ordinary grounded cap/no-input slowdown uses the ground-friction table, while the post-landing trace window carries the native air-deceleration row after airborne sprite contacts; this matches the recorded post-stomp brake much more closely without slowing normal flat walking.
- Flat no-input ground friction now reads the native `kHandlePlayerPhysics_DATA_00D309` table entries `-0x0020`/`+0x0020`; no-input friction is skipped while airborne, matching `HandlePlayerPhysics_00D764()` only calling the friction branch when `player_in_air_flag` is clear.
- Slope contact now feeds `NativeSlopePlayerTable[kind]` back into the horizontal branch as the current `player_slope_player_is_on1` value. That value selects native slope rows in `kHandlePlayerPhysics_DATA_00D535`, `kHandlePlayerPhysics_MarioAccel`, `kHandlePlayerPhysics_DATA_00D309`, and `kHandlePlayerPhysics_DATA_00D5C9`, including the first no-input downslope sliding behavior. Level slope surfaces select the native `$E5C8` steepness table for grassland tilesets `0`/`7` and the default `$E55E` table otherwise, matching `InitializeMap16Pointers()`; this changes level 105 diagonal-pipe tile `0x01C7` from default kind `21` to grassland kind `12`. This still depends on the temporary geometric slope resolver to identify the contact, so exact block-edge behavior remains pending.
- Slope contact also ports the `RunPlayerBlockCode_00EEE1()` fast-toward-peak branch: if Mario is moving at least `0x28` toward a slope peak, vertical speed comes from `kSlopeDataTables_Player_TowardsPeakYSpeed`; slower toward-peak movement falls back to native slope row `32` before the stationary cap is applied.
- Steep-slope overrun now has a dedicated trace bridge for the Yoshi Island 1 post-pipe slope. Native `RunPlayerBlockCode_EB77()` can increment `player_on_ground_flag` when Mario is just above a slope surface but outside the snap distance, then `RunPlayerBlockCode_00EE1D()` sets `player_in_air_flag=0x24` because no floor contact flag was applied. Godot preserves that mixed state as `NativeSlopeOverrunGround`, keeps falling Y speed instead of snapping to the geometric slope, preserves `InAirState` during multi-frame loose steep-pipe ground contact, and requires `InAirState == 0` before P-meter sprint increments or a grounded jump starts. This keeps the first diagonal-pipe contact from incorrectly acting like normal ground while native still reports the mixed ground/air state. This is still a bridge around the temporary line-segment slope solver; the final fix is the full native Map16 act-as/block-code path.
- Normal jump speeds use the 16-entry `kHandlePlayerPhysics_JumpHeightTable`.
- The jump-table lookup is now public as `SmwPhysics.JumpSpeedIndexFor()` / `JumpYSpeedFor()` and exposed through RCON `physics`, so live playtests can verify exactly which native jump row a given X speed and spin state would use.
- The fixed-step order now mirrors the native `PlayerState00_00CD24()` structure more closely: position/collision advances first with the previous-frame speeds, then the `HandlePlayerPhysics()`-style jump, gravity, horizontal acceleration, and P-meter updates prepare speeds for the next frame.
- Gravity uses the native `HandlePlayerPhysics_D930` table entries exposed as `VerticalGravityTable`/`VerticalMaxFallTable`: `0x06` when jump is not held and `0x03` while jump/spin is held in the current simplified in-air branch.
- Grounded frames now pin vertical speed to zero and skip `HandlePlayerPhysics_D930`-style gravity. A one-pixel top-of-solid contact probe preserves grounded state when Mario is exactly standing on a floor, while walking beyond that support clears `OnGround` before gravity starts on the next frame.
- Solid support now uses a native-style X probe instead of the whole 14 px player rectangle when preserving ground or landing on a floor. Rightward movement tests around `x+5`, leftward movement around `x+9`, and neutral movement uses center. The same support rule blocks false step-up/landing on tall pipe-shaft edges, while normal 16 px low ledges still use the broader step-up behavior. Grounded leading-foot carry is capped only at the trailing edge of a support solid, matching the post-Banzai native drop frame without making continuous leading-foot ledges collapse. Upward ceiling hits require the player center to be under the solid so shallow side/corner overlaps do not cancel a jump.
- Isolated 16x16 full-overlap block tops have a separate support mode for the late post-Banzai block/flower sequence. The bridge accepts the native right-edge landing depth, anchors Mario at the observed subpixel position, suppresses the immediate buffered ground jump, and grants a short pass-through window so the following frames do not reinterpret the same block as a side wall. This is intentionally scoped to standalone full-overlap blocks until the native Map16 block-code path can replace the temporary support modes.
- The late level-105 vertical pipe after the flower block has a trace-scoped side-contact bridge. Pipe-top contact for powered airborne Mario keeps the observed native right-wall anchor (`pipe_left - 11.8125 px`) instead of the generic one-pixel wall slack. The same pipe's shaft tiles are emitted as horizontal-only solids, scoped to that object, so the falling side-block contacts repeat while Mario is airborne but cannot turn the shaft into a floor or grounded push-out. The rising-contact skip is also scoped to that exact pipe top at `x=4544`, with a narrow skim cap around `x=4531,y=228..229` to reproduce the native side-block damping while Mario rises onto the pipe cap.
- Airborne horizontal wall contacts keep a one-pixel native slack on normal vertical solids, scoped away from grounded wall impacts and horizontal-only debug solids. Subpixel-only overlaps inside that slack are ignored instead of becoming a wall snap; this preserves the native pipe/Piranha block-column timing after the first flying-block side hit. They also use a side-height probe instead of the whole player rectangle: powered standing Mario checks near `top+26`, while small/ducking keeps the midpoint probe for now. Native-style airborne wall contacts preserve `SubXSpeed` when zeroing the high X speed byte, matching the SMW side-block path more closely through the Yoshi Island 1 TAS pipe/Piranha section.
- Maximum normal fall speed is currently `0x40`, matching the common non-cape clamp in the same table.
- Cape form now ports the first `HandlePlayerPhysics_InAir()` float branch: when cape Mario is falling and holding jump, the runtime starts the native `0x10`-frame float timer and clamps downward `YSpeed` to the first `00D7B9` table value, `0x10`. This is only the fall-cap slice; full cape takeoff, flight phase, dive, glide, and `00D7C8/00D7D4/00D7D9` behavior are still pending.
- Big/cape/fire forms now track a `Ducking` state when grounded and holding down. The temporary duck hitbox uses the 16px small-height footprint and preserves Mario's feet when entering or leaving the state; grounded ducking suppresses horizontal acceleration like the native early ducking branch. The steep-slope overrun and post-pipe kind-13 bridges keep the native trace's special cases: the landing frame can still consume held horizontal input, ducking steep-right push-out preserves falling Y speed and Y subpixels, pure `Down+Y` on that slope carries downhill acceleration instead of clamping at the temporary geometric slope target, and the native ducking launch frame applies the observed `x/subx = native -1:0x30` anchor with a short cooldown to avoid a second synthetic launch.
- Godot `_state.Y` is now treated as the native/visual player anchor, not the collision-box top. Small and ducking forms use a 16 px collision body beginning at `_state.Y + 16`; big/cape/fire forms use a 32 px collision body beginning at `_state.Y`. All current forms therefore share the same `_state.Y + 32` foot anchor while trace comparison can keep using native `player_ypos + LevelVisualYOffset`. Mario's OAM bridge now keeps the native `-1` px Y bias for every form instead of applying a powered-form render-only height delta.
- Fire form now has the first `CheckPowerUpSpecificPlayerAttacks`/`SpawnPlayerFireball` bridge: a run/Y pressed edge creates a capped player fireball using native spawn offsets, native `0x03/0xFD` horizontal speed direction, initial downward speed `0x30`, and the native 10-frame shoot-pose timer. Its motion and terrain bounce are still a temporary extended-sprite approximation until the complete `ExtSpr05_MarioFireball`, extended sprite collision, smoke, and fire-kill normal-sprite branches are ported.
- Horizontal movement is clamped to the generated level bounds so Mario cannot leave the level to the left or right during the playable slice.
- Runtime slope collision is a temporary geometric bridge. Only imported diagonal pipe/ledge/slope edge cells become slope surfaces; slope-family support/fill/assist cells are not emitted as rectangular solids because those temporary AABBs made Mario stand on hidden stair steps inside visual slopes. These surfaces are emitted per Map16 tile rather than as long connected-component averages, which avoids false collision lines when adjacent or overlapping slope objects touch. Standard slope Map16 tiles now use per-tile segment heights: gradual slopes change by 4 px per tile, normal slopes by 8 px per tile, and steep slopes by 16 px per tile. Diagonal pipe floor, body, and underside cells are tracked separately so floor/ceiling slope segments can remain traversable while embedded player positions still get rejected from body cells inside the pipe volume; floor cells are not reused for horizontal body intrusion. The player floor solver now uses the native `x+8` body-center probe for airborne slope landings with no above-surface snap, and tries that native center before side probes while grounded; a narrow native-kind `20..23` side-probe fallback remains for diagonal pipe support so pipe bodies still hold the player while non-pipe slopes avoid the old leading-foot snap. The final fix is still the native Map16 act-as/slope handling path, not this geometric shortcut.
- Diagonal-pipe body recovery now only resolves frames with actual horizontal intrusion. Pure vertical motion inside the temporary pipe-volume cells is left to the slope/ceiling branch so adjacent body cells do not alternately push Mario left and right during a jump trace.
- Ceiling-slope contact now requires crossing from below/inside on the previous frame before zeroing upward motion. This keeps controlled RCON jump probes near the Yoshi Island 1 diagonal-pipe underside from having their native jump speed canceled by a slope segment that Mario was already embedded past because of the temporary geometric resolver.
- The floor-slope probe is shared by the player and the first-pass runtime sprite actors, so imported enemies can stand on the same temporary slope surfaces instead of only interacting with rectangular solids. Sprite actors still use a simpler center probe than the player for now. For trace alignment, level-start actors receive a short active warm-up before the Godot input slice starts, and sprite `0xBD` uses a native-style initial `-2 px/frame` motion with flat-ground slowdown in `1/32 px/frame` increments. Actor horizontal wall resolution now skips floor-support/fill contacts that share the actor's support row; this keeps the level 105 screen-11 Rexes from being pushed to the right edge of a merged ledge-fill rectangle while they are standing on the floor.
- Carryable Koopa shells now have a trace-aligned native bridge for the post-Banzai Yoshi Island 1 section. Grounded side contact while the run/Y button is held promotes shell sprites `0xDA`/`0xDB`/`0xDC`/`0xDD`/`0xDF` into native carried state `0x0B`, keeps them non-interactive while carried, and attaches them to Mario at the observed native offset. Releasing X/Y now detaches carried shells: holding `Up` promotes them to native tossed state `0x09` with upward velocity, while a neutral release promotes them to kicked state `0x0A`. Full sprite-slot parity and complete carry interaction are still pending, but frame captures now verify the pickup and upward-release state transitions against the native recording. Solid block-style actor side contacts use the same trace evidence: the first flying-block side collision leaves Mario stopped with `SubXSpeed=0x80`, not `0x00`, which affects the next acceleration frame.
- RCON `slope_probe` and `trace_sensors` expose the left/center/right floor probes, per-probe Map16/pipe-cell roles, from-above hit decision, and nearby native slope `kind`/`snap` values so pipe and slope collision regressions can be captured without manual screenshots. The regular `trace`/`state` output also includes the loose steep-pipe frame counter/kind, native slope-overrun flag, leading-foot carry counter, and preserved-ground-Y counter so one-frame block-code bridges can be compared against native traces.
- `SMW_DEBUG_COLLISION_TRACE=1` and `SMW_DEBUG_SLOPE_TRACE=1` add low-level physics logs for rect intersections and ceiling-slope candidates during headless/RCON repros. They are intentionally environment-gated because normal traces are already verbose.
- `tools/check-dotnet.sh` runs a C# physics smoke executable that verifies the flat-ground caps, native cap-drag step, P-meter sprint threshold behavior, friction step, imported horizontal max-speed table, native slope table decode, slope-player horizontal slide rows, and native-unit golden trajectories for sustained walk/run, small-jump hold/release, and ledge-fall probes.

## Recording Sync Baseline

The current trace workflow compares a clean native boot recording against Godot without native save states:

- `tools/run-native-input-recording-wayland.sh` records the native `smw/` build from boot, stores timestamped full and level-start `.input` files under `generated/smw/recordings/`, and refreshes stable `latest-*` aliases for the harness.
- `K` is the manual level-start marker when recording. The trace wrapper can also use an automatic active-level marker, but manual `K` is preferred when the user enters the level and wants the Godot slice to begin at that exact point.
- `tools/run-recording-trace-compare.sh` now runs native long enough to reach the marked absolute frame, drops native records before that frame, and then compares against Godot frame 0 from the sliced input.
- The Godot slice intentionally prepends two neutral frames by default (`--godot-input-delay 2`, also used by the visible side-by-side wrapper). Native trace evidence after the move-before-physics patch showed the first 80 player X positions match within roughly `0.001 px` when Godot input is delayed by two frames, so this is treated as the current input-latch phase bridge rather than a physics constant tweak. Pass `--godot-input-delay 0` only when investigating the raw slicer phase.

Fresh trace status from the latest small-Mario Yoshi Island 1 recording:

- Native and Godot now agree on initial `x=16.00` and `powerup=0` at the selected level-start slice, so the earlier Yoshi-house/wrong-level input problem is no longer the active blocker.
- Native raw `player_y=352` normalizes to Godot `y=288` with `--native-y-offset=-64`, and the Godot collision rectangle now stands on the floor through the `+16` collision offset instead of making `_state.Y` fall toward the floor top. The latest trace reports `native_y_adjusted=288.00` and `godot_y=288.00` at the first divergence.
- The rendered Mario OAM is also aligned to that anchor now. A Wayland compositor capture with overlays confirmed the previous hover regression, then `PlayerRenderYOffsetForState()` was reduced to the native `-1` px bias for all forms. The powered-form collision rectangle now extends upward from the same foot anchor instead of shifting Mario's rendered body down independently of the native trace anchor.
- The first horizontal drift was isolated to input-latch phase, not a changed acceleration constant. With raw slicing, after switching to native-style move-before-physics ordering, the first divergence was at index `43`: native reported `x=16, subx=128, xs=6`, while Godot reported `x=17.31, subx=80, xs=9`. Comparing the same traces with Godot shifted two frames later reduced the first-80-frame mean absolute X error to about `0.001 px`, so the recording wrappers now prepad two neutral Godot frames before applying the level-start input slice.
- With that default phase, the 120-frame trace slice now matches all comparable player position and power-up records within the current `1 px` tolerance. Extending the run to 600 frames moved the next known divergence to index `125`, after the first jump/stomp sequence: both sides reported `xs=20` and matching Y, but Godot was about `1.06 px` ahead with a different horizontal subspeed. That pointed at the post-landing cap/no-input brake using normal ground friction; the Godot physics core now carries native air-deceleration during a bounded post-landing trace window while preserving the flat walk/run golden trajectories.
- Enemy sync is now part of the same trace surface. Godot live traces include nearest actor id/state/position/speed/active fields, and the native reference trace exposes the nearest normal sprite slot/id/status/position/speed/subpixel fields. The first `0xBD` sliding Koopa now starts much closer: at Godot/native trace index `0`, both X positions are `162`, and by index `42` native is `x=91,y=368` while Godot is `x=90.69,y=304`, matching after `LevelVisualYOffset`. Remaining enemy work is to promote these fields from diagnostics to comparator checks and port exact activation, state, and hitbox behavior.
- Runtime sprite collision is now being pulled toward the native clipping tables instead of visual rectangles where it does not break the current recording trace. The level 105 actors that showed obvious placement drift use the LMU/native clipping entries for Banzai Bill (`0x9F`: `+8,+8,52x46`), Rex (`0xAB`: `+2,-8,12x19`), and Clappin' Chuck (`0x95`: `+0,-4,15x16`). Banzai/Rex also spawn from their native sprite origin, which keeps the rendered OAM and collision surface tied to the same coordinate system. Sliding Koopa (`0xBD`) stays on the broader current player-contact rectangle for now because applying the sprite/sprite clip table made the first recorded stomp bounce about 6 px too low; it needs the exact Mario-vs-sprite contact routine, not a table-only swap.
- Dragon Coin collection no longer uses the full rendered `16x32` Map16 area. The pickup surface is narrowed to a top-aligned `8x30` sensor rectangle (`x+4`, `y+0`), closer to the original block-sensor behavior where touching the coin's top or bottom Map16 tile triggers `EraseYoshiCoin` rather than arbitrary sprite-rectangle overlap. `pickups_near` / `coins_near` RCON commands now list the active pickup rectangles, debug overlays draw the pickup hitbox separately from the visual tile marker, and recording trace comparison now checks native `coins`/`yoshi_coins` against Godot `coins`/`dragon` so early Dragon Coin pickup regressions show up in the first-divergence report.
- The latest guards match 930, 1800, 2400, 3000, 3030, 3600, and 4200 comparable frames against a clean native build. The current post-Banzai pass fixed the stale `0x0080` ground rest subspeed before the carried-shell run-up, the carried-shell Banzai normal-bounce/top-band contact frame, carried-shell upward release to state `0x09`, the immediate airborne center-support landing on `ground_edge_top`, the next grounded leading-foot ledge release where native drops at index `3524`, and the later single-block/flower sequence where native uses full-overlap block-code support and flips big Mario to fire on the collection frame. The post-4200 diagnostic now reaches index `4537`; the remaining mismatch is around the goal walkout/course-clear area, where Godot is about one pixel ahead and the shell is kicked on the ground while native's nearest sprite is the goal tape. The current slope/transition findings are: steep diagonal-pipe native kinds `20..23` can set the ground bit while preserving falling Y speed for a few frames before a jump; grassland tilesets `0`/`7` remap some diagonal-pipe Map16 IDs from default steep kinds to kind `12`/`13`; kind-12 ledge slopes need integer native-style probes plus a directional one-pixel floor adjustment on fast rightward contact; low-speed powered kind-12 turnaround jumps can carry an extra `0x0080` horizontal subspeed only when entering with zero subspeed; the underworld `1CB -> 105` return pipe depends on the secondary-entrance screen bits in `$05FC00`, not only the X-position index; and the post-pipe kind-13 ducking slope needs both a native launch subpixel anchor and the later leading-foot edge support frame. Mushroom collection while already powered now follows reserve-item behavior and does not start the growth freeze. Godot traces now include grouped Rex diagnostics through `track_ab_all`, and native temporary slot tracing confirmed the screen-11 Rex blocker was a Godot actor floor-fill wall resolution bug rather than native keeping those Rexes at the right edge.

This is not a complete reimplementation of every SMW physics branch yet. Missing pieces include the full native Map16 act-as/slope interaction table, ice, swimming, full cape flight, carrying, Yoshi, rope/net climbing, solid-sprite interaction, and exact takeoff behavior. The purpose of this slice is to establish the deterministic Godot core, asset feed, and regression surface before broadening the compatibility matrix.

## Exact-Port Rule

When porting a physics branch, prefer a direct translation of the original state variables and tables over an idiomatic approximation. Rename only at the boundary where it improves Godot integration; keep internal units and timer semantics close enough that trace comparisons against the native reference can be automated.

## Reference Sources

Hamaluik's "Super Mario World Physics" article is useful as an external feel check, not as the 1:1 source of truth. It measured motion from video at 60 Hz with short Mario treated as 1 meter tall, then fit linear/quadratic regressions:

- Walking: about `3.7 m/s`, from the displayed fit `x = 3.698t - 0.229`.
- Running: about `9.1 m/s`, from the displayed fit `x = 9.091t + 0.039`.
- Small jump: displayed fit `y = -33.910t^2 + 17.361t - 0.018`, which implies about `67.82 m/s^2` downward acceleration and `17.36 m/s` initial upward velocity in that normalized scale.
- High jump: displayed fit `y = -17.396t^2 + 15.209t + 0.007`, implying about `34.79 m/s^2` downward acceleration and `15.21 m/s` initial upward velocity.
- Falling: displayed fit `y = -27.940t^2 - 1.057t + 2.477`, implying about `55.88 m/s^2` downward acceleration.

The direct implementation targets are the native SMW routines and tables:

- Horizontal movement: `HandlePlayerPhysics()`, `HandlePlayerPhysics_00D742()`, `HandlePlayerPhysics_00D772()`, `HandlePlayerPhysics_UpdatePMeterEx()`, and tables `kHandlePlayerPhysics_DATA_00D535`, `kHandlePlayerPhysics_MarioAccel`, `kHandlePlayerPhysics_DATA_00D2CD`, `kHandlePlayerPhysics_DATA_00D309`, `kHandlePlayerPhysics_DATA_00D5C9`, and `kHandlePlayerPhysics_DATA_00D5EB` in `smw/src/smw_00.cpp`.
- Jump and gravity: `kHandlePlayerPhysics_JumpHeightTable`, `HandlePlayerPhysics_InAir()`, `HandlePlayerPhysics_D930()`, `kHandlePlayerPhysics_DATA_00D7A5`, `kHandlePlayerPhysics_DATA_00D7AF`, and cape-specific `00D7B9/00D7C8/00D7D4/00D7D9` tables.
- Slope collision: `InitializeMap16Pointers()` slope-table selection, `RunPlayerBlockCode_EB77()`, `RunPlayerBlockCode_00EEE1()`, `kSlopeSteepness_e55e`, `kSlopeSteepness_e5c8`, `kSlopeDataTables_ShapeOfSlope`, `kSlopeDataTables_Player`, `kSlopeDataTables_Player_StationaryYSpeed`, `kSlopeDataTables_Player_TowardsPeakYSpeed`, `kSlopeDataTables_Player_SnapToSlopeDistance`, and `kSlopeDataTables_SlopeType`.

Current slope bridge status: Godot still resolves slopes through generated per-Map16 line segments, but each segment now carries decoded native slope metadata from the SMW tables: slope kind, player slope value, slope type, stationary Y-speed cap, and snap distance. The resolver uses the generated level header tileset to choose `$E55E` or `$E5C8`, so Yoshi Island 1's tileset `7` diagonal-pipe cells decode through the same table as native. `state`, `trace`, and collision RCON probes expose these fields so slope bugs can be compared against `RunPlayerBlockCode_00EEE1()` table behavior. Map16 rows whose native snap distance is zero are kept as kind diagnostics but continue using the geometric fallback tolerance until the full native block-interaction path replaces the temporary line solver.

Tortellini (`https://github.com/ToadsworthLP/Tortellini`) was reviewed as a Godot/C# Mario-style controller reference. It is MIT-licensed and useful for structure: explicit stand/walk/run/long-run/jump/spin-jump/fall/crouch/slide states, floor-normal driven slope behavior, and Godot snapping flow. It is not a source of truth for this port's constants because it targets a Godot 3-era 3D controller with exported feel parameters such as `WalkSpeed`, `RunSpeed`, and jump forces rather than SMW ROM units and native tables.
